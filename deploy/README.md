# Развёртывание и проверка изменений

## Конфигурация

Используйте `DJANGO_SETTINGS_MODULE=config.production` и значения из
`.env.production.example`. Замените домены, пароль БД и шаблон ключа.
Проект загружает `.env`; переменные окружения процесса имеют приоритет.
Чтобы использовать production-образец как файл, скопируйте его именно в `.env`
на сервере. Не переносите локальный `.env` на публичный сервер.

Новый секрет можно создать командой:

```sh
python -c "import secrets; print(secrets.token_urlsafe(64))"
```

Сохраните результат в `DJANGO_SECRET_KEY`. Production-конфигурация откажется
запускаться с DEBUG, пустым/произвольным списком хостов, коротким ключом или
шаблоном из примера. Существующий локальный ключ не заменяется; локальные
пользовательские сессии сохраняются.

`DJANGO_TRUST_PROXY_HTTPS=True` допустим только за доверенным прокси, который
перезаписывает `X-Forwarded-Proto`. Приложение должно слушать только loopback
или приватный интерфейс, закрытый от клиентов. В nginx-примере upstream —
`127.0.0.1:8000`, а `APPLICATION_TRUSTED_PROXY_IPS=127.0.0.1,::1` разрешает
использовать перезаписанный nginx заголовок `X-Real-IP`. Без явно доверенного
адреса заголовки клиента не влияют на IP для лимитов. Поддерживаются отдельные
IP-адреса, а не CIDR-диапазоны.

## Установка

```sh
python -m pip install -r requirements.txt
python manage.py migrate --noinput --settings=config.production
python manage.py check --deploy --fail-level WARNING --settings=config.production
python manage.py collectstatic --noinput --ignore=php --ignore='*.php' --settings=config.production
```

Запустите WSGI/ASGI-приложение совместимым production-сервером с переменной
`DJANGO_SETTINGS_MODULE=config.production`. Сервер приложения, ОС, домен и TLS
настраиваются на целевом хосте; `runserver` предназначен для разработки.

Статика собирается в `staticfiles/`; пользовательские изображения остаются
в `media/`. PHP исключается только из публикуемого набора; исходные файлы,
CSS/JS и демоматериалы не удаляются и не переписываются. Сжатие и минификация
не добавлены. Шаблон nginx блокирует PHP и не содержит исполняющего обработчика.

`deploy/nginx.conf.example` подключается внутри `http {}`. Замените пути,
`example.com` и сертификаты, затем выполните `nginx -t` на сервере до reload.
Проверьте, что на хосте загружается стандартная таблица `mime.types`.
Шаблон ограничивает размер, время и одновременные соединения загрузок,
включая `/ky/` и `/tr/`, и перенаправляет HTTP на HTTPS.

HSTS в приложении начинается с 3600 секунд. Увеличивайте срок после проверки
HTTPS; включение для всех поддоменов и preload вынесено в отдельные параметры.
Предупреждения Django W005/W021 об этих двух необязательных настройках
явно отключены: проект не предполагает, что все поддомены уже работают по HTTPS,
и не включает домен в браузерный preload автоматически. Остальные deployment
checks продолжают выполняться.

## Защита форм и файлов

- `APPLICATION_POST_LIMIT=20`, `APPLICATION_POST_WINDOW=600`: POST на каждую
  форму с одного адреса. Повторные и невалидные запросы тоже расходуют лимит.
- `APPLICATION_GET_LIMIT=120`, `APPLICATION_GET_WINDOW=60`: получение каждой
  формы с одного адреса. Языковые версии используют общий лимит.
- Счётчики хранятся в таблице `core_applicationrequestlimit`; увеличение
  атомарное и общее для всех процессов. Сырые IP в ней не сохраняются.
  Просроченные строки удаляются небольшими порциями при обращениях к формам.
- Ошибка БД лимитера возвращает 503, превышение частоты — 429,
  превышение размера — 413. Отклонённая загрузка не создаёт заявку.
- Резюме ограничено 5 МиБ, суммарное тело career-запроса — 6 МиБ,
  membership и contacts — 64 КиБ. Upload-handler прерывает слишком большой поток до
  сохранения заявки. Ограничения nginx действуют ещё до приложения.
- SVG принимаются в UTF-8, статичные изображения проверяются декодером
  с лимитом 20 миллионов пикселей. PDF проверяются структурно: до 50 страниц,
  ограниченное количество объектов и объём распаковки. Шифрование, активные
  действия, скрипты и вложения отклоняются; байты принятого резюме не меняются.
  Проверка формата не заменяет антивирусную проверку на рабочих местах.

## Кеш и БД

Меню и настройки кешируются на 300 секунд (`SITE_CONTENT_CACHE_TIMEOUT`).
Изменения через обычное сохранение/удаление модели инвалидируют кеш после commit;
незавершённые транзакции не публикуются. Язык и выделение меню вычисляются
отдельно для запроса. При сбое кеша сайт читает данные из БД.

Файловый кеш `tmp/site-cache` общий для процессов на одном хосте. Доступ к нему
должен иметь только пользователь приложения; не размещайте его под static/media.
Для нескольких хостов замените backend alias `site_content` на общий кеш.
Пакет клиента такого backend нужно добавить отдельно. При прямом `QuerySet.update`,
bulk-операциях или SQL сигналы Django не вызываются: после commit вызовите
`core.site_cache.invalidate_site_content()` либо дождитесь TTL.

SQL главной на базе с миграционными данными: 12 запросов до изменений,
7 после прогрева кеша; компании и правление — с 6 до 2. Это счётчики запросов,
а не измерение времени ответа PostgreSQL. Индексы поиска следует выбирать
по EXPLAIN на реальных объёмах. На текущей локальной базе (11 компаний,
10 новостей, без вакансий) планы проверены, новые индексы поиска не добавлены.

## Проверки

```sh
python manage.py test core --settings=config.test_settings --noinput
python manage.py makemigrations --check --dry-run --settings=config.test_settings
python manage.py test core --settings=config.test_postgres_settings --noinput
python -m pip check
```

SQLite-тесты используют БД и файлы в памяти. PostgreSQL-тесты создают отдельную
БД `test_<DB_NAME>`; используйте отдельную тестовую роль с CREATEDB и отдельные
настройки соединения. Не выдавайте CREATEDB рабочему пользователю ради тестов.
Тест параллельного лимитера проверяет, что восемь отдельных соединений не могут
получить больше трёх разрешений из общего бюджета; на SQLite он пропускается.

GitHub Actions запускает оба варианта тестов, проверяет миграции, production
settings, сборку статики и зависимости через pip-audit при push и pull request.

## Обратная связь и карта

Обращения со страницы «Контакты» сохраняются в разделе **Контент → Сообщения
с сайта** в админке. Для сотрудников выдайте права просмотра/изменения этой
модели. Email-уведомления не настроены; новые обращения видны на главной админки.

В **Общие настройки → Карта 2ГИС** укажите ключ RasterJS API из Менеджера
Платформы 2ГИС. Без ключа или при недоступности карты посетителю остаётся
точная ссылка на здание. Карточка организации для этой карты не требуется.
